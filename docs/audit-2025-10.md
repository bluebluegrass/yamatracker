## Application Architecture Snapshot
- Next.js 15 App Router with a top-level locale segment (`src/app/[locale]`) powered by **next-intl** middleware (`src/middleware.ts`). Locale layout wraps pages with `NextIntlClientProvider` and the toast context.
- Client-side pages (`'use client'`) handle all main UX today: the localized home/landing page instantly redirects to `/dashboard`; `/dashboard` renders the tracker; `/login` and `/signup` handle Supabase email/password auth; `/u/[slug]` is a public profile view (currently blocked by RLS, see below).
- Styling combines Tailwind CSS 4 via global import (`styles/globals.css`) with bespoke utility classes for mountain cards and progress indicators. No component-level design system yet.
- Shared UI primitives sit in `src/components/**` with a dashboard folder for progress widgets, a chat assistant module, and sharing utilities (QR code + canvas export).

## Architecture Overview
- **Framework:** Next.js 15 App Router, locale-based routing, Tailwind CSS, next-intl for i18n.
- **State Management:** User action → Component → Hook → Supabase → UI update. Main state flows through hooks (`useMountainCompletions`, `useAuth`).
- **Data Models:**
  - `users`: { id, username, slug, locale, created_at }
  - `mountains`: { id, name_ja, name_en, name_zh, region, prefecture, elevation_m, difficulty, created_at }
  - `user_mountains`: { user_id, mountain_id, completed_at, hiked_on, source }
- **Aggregates:** Derived from DB views (`v_altitude_buckets`, `v_mountains`) and `dashboard_snapshot` RPC.
- **Components:** Dashboard widgets (progress, difficulty, badges), tracker dashboard, profile card, sharing utilities, chat assistant.
- **Routing:**
  - `/[locale]/page.tsx`: Landing page
  - `/[locale]/dashboard/page.tsx`: Main tracker
  - `/[locale]/tracker-v2/page.tsx`: Redesign tracker (feature-flagged)
  - `/u/[slug]/page.tsx`: Public profile
  - `/api/*`: API endpoints for chat, snapshot, etc.

## Single Source of Truth
- **Completion State:** Supabase `user_mountains` table is the canonical source. Client state mirrors DB via hooks; all aggregates (region, difficulty, altitude) are derived from DB views and RPCs.
- **Desync Risks:**
  - Local UI state may temporarily diverge if optimistic updates fail or network errors occur.
  - All dashboard widgets must read from the same queried dataset to avoid badge/progress/desync.

## RLS Policy Implications
- **users:** Can only read/update own profile. Separate policy for INSERT during signup.
- **mountains:** World-readable (SELECT only).
- **user_mountains:** Can only read/write own completions. Policy for updating `hiked_on` date.
- **Profile Page:** `/u/[slug]` must not expose private fields (user_id, email). Current fallback to test user if RLS blocks access.

## State Management Patterns
- Hooks (`useMountainCompletions`, `useAuth`, `useToast`) manage local state and sync with Supabase.
- All updates (toggle, set date) go through Supabase and update local state on success.
- Dashboard aggregates are fetched via RPC (`dashboard_snapshot`) for consistency.

## i18n
- Locales: en, ja, zh. All UI copy and region names are localized via next-intl and message files.

## Routing & Key Components
- `src/app/[locale]/page.tsx`: acts as the landing page but auto-redirects to `/dashboard` after 2 seconds. Includes static CTA copy and locale switch links.
- `src/app/[locale]/dashboard/page.tsx`: main tracker view. Fetches mountain list from Supabase on mount, groups mountains by region, surfaces progress widgets, badges, and an embedded chat guide. Uses `useMountainCompletions` for completion state and `useToast` for feedback.
- `src/app/u/[slug]/page.tsx`: intended public profile. Queries `users` and `user_mountains` by slug using the public Supabase client. When RLS blocks access it falls back to a hard-coded “test user”, signaling the page is not yet wired to a secure, public-friendly data shape.
- `src/app/api/chat/route.ts`: edge-compatible recommendation endpoint. Uses `supabaseAdmin` (service key) to read the full `mountains` table and filter suggestions server-side. Includes ad‑hoc rate limiting, heuristic filtering, and logging.
- `src/app/api/debug-snapshot/route.ts`: defers to `getSnapshot` RPC (`dashboard_snapshot`) to return authoritative aggregates for the authenticated user. Currently used as a debugging endpoint, not by the dashboard UI.
- `src/app/api/og/route.tsx`: generates social previews for profiles by slug via server-side Supabase reads.

## Data & State Management
- **Auth**: `useAuth` wraps Supabase client auth session tracking; consumers call `supabase.auth.signInWithPassword` or `signUp` directly from pages. There is no global auth provider besides Supabase’s native session.
- **Completion state**: `useMountainCompletions` is the client-side source. It loads `user_mountains` rows for the logged-in user, keeps `completedIds` + metadata in component state, and performs writes (`insert`, `delete`, `update`) directly against the table. Toasts provide optimistic UX; the hook does not refetch after updates.
- **Mountain catalog**: `Dashboard` fetches `supabase.from('mountains').select('*')` client-side. A legacy JSON file (`src/lib/data/mountains.json`) still exists and is used by helper tools (e.g., chat heuristics) but not by the main grid.
- **Aggregations**: Dashboard widgets recompute stats locally from the fetched lists (`DifficultyBreakdown` derives counts client-side). Database-side RPCs (`dashboard_snapshot`, `toggle_completion`) provide consistent aggregates but are unused in the UI, leading to two parallel data flows:

```
User clicks mountain → Dashboard page → useMountainCompletions → Supabase (user_mountains)
                                 ↘ local state + client aggregations

Supabase (RPCs)
  └── dashboard_snapshot() → /api/debug-snapshot (manual check)
```

- **Chat assistant**: Relies on full mountain metadata (difficulty, elevation, season heuristics) fetched with the service key. Outputs suggestions to the client component; no shared state with tracker completion data.

## Database & Supabase Layer
- `db/schema.sql` defines three core tables (`users`, `mountains`, `user_mountains`). However, the schema file omits `difficulty` and other columns that `db/seed_mountains.sql` and runtime code expect (difficulty stars, physicality, reference schedule). The Supabase instance must already include these fields; the repository schema is stale and risks misprovisioning new environments.
- `db/views_and_rpcs.sql` introduces:
  - `v_mountains`: exposes `difficulty_int` (string length) for star ratings.
  - `dashboard_snapshot(uid)` (security definer) that returns totals, per-region, per-difficulty stats, and badge keys.
  - `toggle_completion(mountain_id, mark, uid)` (security definer) to mutate completions and return a fresh snapshot.
- `supabase/migrations/20250111_add_hiked_on_to_user_mountains.sql` adds `hiked_on` and an update policy, but does not update RPCs or client hooks to expose the field in aggregates.
- Service clients:
  - `src/lib/supabase/client.ts`: anon key for browser interactions.
  - `src/lib/supabase/server.ts`: service-role key for server routes; used by chat API and OG generator.

## Row-Level Security (RLS)
- `users`: `USING auth.uid() = id` for SELECT/UPDATE, plus separate INSERT policy to allow signups. Result: authenticated users can only read their own profile row; public profile route cannot access other users.
- `mountains`: explicitly world-readable (`USING true`). Safe for public clients.
- `user_mountains`: policy restricts reads/writes to owner (`auth.uid() = user_id`). Migration adds explicit update policy for `hiked_on` edits. Any server-side feature that needs cross-user access (e.g., public profiles) must go through a service role or a dedicated view with laxer RLS.
- RPCs (`dashboard_snapshot`, `toggle_completion`) run as definer and return only aggregated data scoped to the caller. They are granted to `authenticated` (and `anon` for `dashboard_snapshot`).

## Single Source of Truth & Desync Risks
- Authoritative completion state resides in `public.user_mountains`. Client hook caches a copy but does not resync after writes, so network errors or concurrent updates can desync UI until a full reload. The presence of RPC-powered snapshots suggests an alternate, more consistent data pipeline, but it is currently unused.
- Mountain metadata exists in three places:
  1. Supabase `mountains` table (authoritative for the app).
  2. `db/seed_mountains.sql` (includes difficulty/physicality columns).
  3. `src/lib/data/mountains.json` (partial fields, missing difficulty). Divergence between these sources can break aggregates, chat heuristics, and tracker filters.
- Public profile route tries to read `users` via anon client; RLS blocks it. The fallback fake data hides the issue but means actual slugs never render. A dedicated RLS-safe view or server-side fetch is required to avoid leaking private columns while keeping the feature functional.
- Supabase RPCs compute region/difficulty totals server-side; dashboard recomputes in the browser. Without aligning on one source, future additions (e.g., altitude buckets) risk double maintenance and mismatched results.

## Debuggability Notes
- Extensive `console.log` statements remain in dashboard and signup flows, aiding debugging but noisier for production. No error boundary or toast for mountain fetch failures beyond a single error state.
- There are numerous experimental routes under `src/app/[locale]/*-test` that appear unused; they may confuse routing or increase bundle size if deployed.
- No automated tests; validation relies on manual checks and Supabase console.

## Immediate Gaps Toward Target UX
- Landing page is effectively a redirect screen; needs full hero/feature content.
- Tracker lacks sidebar filtering, interactive map, or aggregate dashboards (difficulty card only; no altitude buckets or totals beyond simple counter).
- Public profile is nonfunctional because of RLS and lacks the name-card presentation.
- State synchronization depends on client hooks and lacks a structured data access layer that could feed landing/profile/map consistently.
